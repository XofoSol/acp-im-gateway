# v1.1 — the chat must read like the CLI, plus safe auto-approval

Owner-visible acceptance (the owner is the judge): after a task, and **without sending a single
extra message**, the chat must show:

1. what the agent says, as it says it;
2. every command it runs, verbatim, with its real output;
3. every file it writes or edits, with its path;
4. whether it finished, and the outcome (did the tests run, did they pass);
5. and it must be obvious that it is still alive while it works.

If the owner cannot follow the turn from the chat alone, the work is not done.

## Part A — rendering rules

- **Turn transcript, not one blob.** While the agent works, keep updating the current message in
  place (editMessageText), but never more often than GATEWAY_EDIT_INTERVAL (~1.2s) per chat.
- **Overflow as an ordered log.** When the message would pass ~3500 characters, freeze it and start
  a new message. The chat must read as a sequence of readable blocks, never one giant edited blob.
- **Tool calls are first class.** One line per call, e.g. `$ <the exact command>` for shell calls,
  with the real output fenced underneath, truncated to GATEWAY_TOOL_OUTPUT_LINES (default 15) plus a
  `… (+N more lines)` marker. File writes/edits show `✏️ <path>` and a short diff or excerpt.
- **Reasoning is available but quiet.** Render agent thought chunks inside a Telegram spoiler
  (`<tg-spoiler>`), or omit them when GATEWAY_SHOW_THINKING is off (default: spoiler on).
- **Lifecycle notices.** Start (⏳ with project and model), finish (✅ with the agent's last words and
  a test summary when a test command ran), cancelled (⏹️), error (❌ with the reason).
- **Heartbeat.** If a turn shows no visible change for GATEWAY_HEARTBEAT_SECONDS (default 60),
  refresh with the elapsed time, so the user can see it is alive rather than hung.
- **Telegram limits are hard rules.** 4096 characters per message (chunk longer content), at most one
  write per second per chat, and keep well inside 20 messages/minute in a group — prefer editing over
  posting. HTML parse_mode with correct escaping, so agent output can never break the message.
- **Threads.** Inside a forum topic, reply into the same thread (`message_thread_id`).

## Part B — approval tiers (approved item)

Two lists in configuration, per chat (global defaults, per-chat override):

- `auto_allow` — harmless and read-only. Approve silently (no tap), and log it at INFO.
  Defaults: `git status`, `git diff`, `git log`, `git show`, `git branch`, `git remote -v`, `ls`,
  `cat`, `head`, `tail`, `grep`, `rg`, `find`, `pwd`, `wc`, `pytest`, `python -m pytest`.
- `always_ask` — money or irreversible. MUST still require a tap **even when the posture is
  auto or yolo**: this is a code gate, not a posture, and it wins over `auto_allow`.
  Defaults: `fal.ai`, `fal_client`, `FAL_KEY`, `elevenlabs`, `openai`, `anthropic`, `stripe`,
  `curl` with a data-creating method, `deploy`, `rsync`, `scp`, `wp `, `rm -rf`,
  `git push`, `git reset --hard`, `docker push`, `npm publish`, `aws `, `gcloud `, `hetzner`,
  `cloudpanel`.
- Anything else follows the chat posture (default `ask`).

Matching must be case-insensitive and must inspect the permission request's `toolCall.kind`,
`toolCall.title` and the `rawInput` JSON payload (shell command string, generic tool arguments) plus
the affected file locations. Log every decision at INFO with the reason, so the journal explains
why something was auto-approved or forced to a tap.

Tests: each pattern tier, `always_ask` beating `auto_allow`, a bash payload and a generic
tool-call payload, and an unknown command falling back to `ask`.
